7. 运行时代码读点：`apps/*.js`（尤其 apps/agent.js 3978 行）、`model/**`（各子系统）

## 分类（统一用这 7 类打标签）
- `O` 多源默认冲突：同一 key 在 yaml / 锅巴 / Web / README / 代码默认值中默认值或选项集不一致
- `D` 同义重复/双开关：两个以上开关/字段控制同一效果（含历史遗留字段）
- `P` 覆盖顺序矛盾：注释声称「A 覆盖 B / 优先级 X>Y」，但代码实际相反或都不生效
- `F` 假值陷阱：代码用 `||` / 三元判断把合法的 `0`、`""`、`false` 当未设置，导致配置不生效或静默回退
- `N` 死配置/未接线：yaml 有、面板有，但运行时根本没人读；或读了但约定行为未实现
- `L` 逻辑忽略配置：配置写了一套，代码硬编码另一套（阈值、超时、名字、上限、权限）
- `X` 文档/注释不符：yaml 注释、锅巴 bottomHelpMessage、README 与实现矛盾（含数值、默认、枚举）

## 输出契约（每位审计员一份）
写到自己的文件：`audit/findings/<你的名字>.md`

```md
# <审计范围> 发现

## 结论摘要（5~10 条，按严重度）
1. [P0] ...（一句话）

## 明细
### C<编号> [严重度 P0|P1|P2] [类别 O] 短标题
- 证据 A：`文件:行号` 原值/原文（贴关键片段）
- 证据 B：`文件:行号` 原值/原文
- 打架点：一句话说清两边怎么冲突、运行时会怎样
- 影响面：哪个功能/哪些用户会遇到
- 建议：保留哪个真源、怎么改（不要求你改代码）
- 置信度：高/中（中=需 Lead 复核）
```

硬要求：
- 每条都要有**双侧证据 + 行号**；只读代码/配置得出的结论，禁止臆测（拿不准标「中」）。
- 同一现象不要按 key 拆成 N 条凑数；按**根因**归并。
- 只读审计：**不要修改任何源码/配置**，只写自己的 findings 文件（这就是你的唯一写作用域）。
- 最后用 `send_message` 向 lead 报：文件路径 + P0/P1 条目清单（每条一行）+ 总条数。
